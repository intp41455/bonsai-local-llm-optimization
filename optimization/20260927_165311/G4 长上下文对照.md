# G4 长上下文跨请求复用对照实验 — `--cache-ram` 1024 / 2048 / 4096 / 8192

- 执行时间：2026-09-28 00:21–00:41（Asia/Shanghai）；四臂起始时刻分别 2026-09-28 00:26:04 / 2026-09-28 00:30:32 / 2026-09-28 00:36:01 / 2026-09-28 00:38:52
- 执行方：TRAE Agent
- 授权：用户批准按推荐执行，即对 G4（C1）**残余风险第 1 项**做长上下文跨请求复用验证；
  对照臂需临时改 `backend.extra_args`（生产配置），已在执行前于对话中说明
- 目标风险（引自 `changes.md` 14.3 第 1 项 / 母本第十节）：
  「单个 64 K 宿主检查点约 1.88–2.03 GiB > `--cache-ram 1024` 上限 → 长上下文检查点可能无法保留、TTFT 可能回归」
- **结论：风险落实，因果坐实；可用门槛落在 2048 与 4096 之间（2048 无效、4096 有效）**
- 生产配置已恢复 `--cache-ram 1024`，与变更前字节一致（§6）

## 1. 方法

固定长上下文样本 = `capture\req_001_192027.json`（真实 Agent 请求，296,318 B，sha256 `D7FEBA8FD7370A3F…`，
实测 `prompt_n = 64,396`）。位移样本 = `capture\small_012_221958.json`（20,541 B，sha256 `CD0C2AA92E3DC789…`，
实测 `prompt_n = 7,687`）。

请求走**与生产完全相同的转换管线**（`slim_tools` → `harden_tool_schemas` → `apply_tool_error_policy` →
`apply_thinking_policy`，即 `bonsai_proxy.prewarm()` 所用的同一组函数），直连后端 `127.0.0.1:8081`
（`stream=false`、`max_tokens=1`）——`max_tokens=1` 只影响生成、不改动提示前缀，对 KV 复用无影响。
判据取自后端返回的 `timings.prompt_n`（未命中、真正重算的 token 数）与 `timings.cache_n`（复用的 token 数），
并以 `/metrics` 增量与 `llama-server.log` 的 prompt-cache 淘汰行作旁证。

每臂四步；同一后端二进制、同一 `n_ctx=65536`、同一 `-ctk/-ctv q4_0`，**唯一变量是 `--cache-ram`**：

| 步骤 | 请求 | 作用 |
|---|---|---|
| A1_cold | req_001（64 K） | 冷启，建立本臂基线 |
| A2_same | req_001（同一份） | 槽位仍持有该前缀 → 测“紧接复用” |
| B_intervene | small_012（7,687 tok，内容不同） | 把槽位顶走 → 64 K 的 KV 只能靠**宿主 prompt cache** 存活 |
| A3_again | req_001（同一份） | **决定性步骤**：宿主缓存是否保住了 64 K 检查点 |

各臂配置与进程（漂移检出 → `launcher up --no-prewarm` 空闲受控重启后端；代理 pid 40480 全程未重启）：

| 臂 | config sha256 | 配置指纹 | 后端 pid |

- **A3 分水岭**：1024 与 2048 均为 `cache_n=0`、需重算 64,396 token（≈118 s，与冷启等同）；
  4096 与 8192 为 `cache_n=64,392`、耗时 0.65 / 0.85 s ——相差约 **170 倍**，且与冷/热之别一致。

## 3. 机理证据（日志原文）

- `cram1024` / A1_cold：A1 冷启，槽位按 LRU 选取（缓存里没有可用长条目）（prompt_n=64396，cache_n=0，Δ淘汰=1）
- `cram1024` / A2_same：A2 命中来自**槽位 KV**（LCP 相似度 1.000），不是宿主缓存（prompt_n=4，cache_n=64392，Δ淘汰=0）
- `cram2048` / A3_again：A3 启动即淘汰 `size = 1881.320 MiB` 的条目——64 K 检查点被存进去又被挤掉（prompt_n=64396，cache_n=0，Δ淘汰=1）
- `cram4096` / A3_again：A3 经 LRU 选槽却拿到 cache_n=64,392：由宿主 prompt cache 复原（prompt_n=4，cache_n=64392，Δ淘汰=0）

补充：

- 变更前（`--cache-ram` 默认 8192）进程日志中确实存在 **`size = 2030.278 MiB`** 的 64 K 条目并被淘汰
  （`llama-server.log` 第 1171 行，属变更前进程）；变更后 1024 进程在本实验之前最长只到 `n_tokens_max = 7,096`，
  从未产出过该量级条目——这正是此前“未验证”的原因。
- 2048 臂 A3 的淘汰行 `size = 1881.320 MiB` 是最直接的机理证据：**64 K 检查点被写入宿主缓存，
  但因几乎占满 2,048 MiB 预算，被紧随其后的插入立即挤掉**，等于白存。
- 4096 与 8192 臂全程 0 次淘汰，检查点在 B 顶走槽位后仍可复原。

## 4. 结论（可直接替换 14.3 第 1 项）

1. **残余风险落实**：`--cache-ram 1024` 下，64 K 检查点在槽位被其它请求顶走后**无法从宿主 prompt cache 复原**，
   跨上下文复用丢失，TTFT 从 0.3 s 级回落到 **118 s 级**（= 冷启全量 prefill）。
2. **因果坐实**：同请求、同后端、同 n_ctx，仅 `--cache-ram` 不同 → 4096 / 8192 复原、1024 / 2048 不复原。
3. **门槛**：2048 **不足**（64 K 检查点约 1.88–2.03 GiB，几乎是上限全部）；4096 **有效**。
4. **影响边界（重要，勿扩大）**：受损的是「切走再回来 / 跨上下文」的长上下文复用；
   **单条对话内继续追问（前缀增长）不受影响**（A2 三臂均完全复用）。

## 5. 内存代价（同口径 perfmon `\Process(llama-server)\Private Bytes`）

| 时点 | 缓存内容 | Private Bytes |
|---|---|---|
| 1024（变更后 v3 快照，23:13:36，uptime 7m57s） | 仅小额条目 | 10,262,142,976 B = **9.56 GiB** |
| 8192（本实验 00:31:03，持有一个 64 K 检查点） | 64 K | 10,750,976,000 B = **10.01 GiB** |
| 4096（本实验 00:41 前后，持有一个 64 K 检查点） | 64 K | 10,748,936,192 B = **10.01 GiB** |

- 8192 与 4096 两臂在“均持有 64 K 检查点”时几乎完全相同（差 ~2 MB）→ 该时点占用由**实际缓存内容**决定，不由上限决定。
- 与 1024 快照相比 +0.45 GiB，但两者 uptime / 缓存内容不同，**不得当作“升档代价 = 0.45 GiB”**。
- 上限本身之差才是配置层代价：4096 − 1024 = **3,072 MiB**；按 14.2 已验证的近似 1:1 关系，
  缓存被填满时的宿主开销上限即此值。
- 全机瞬时计数器（Available / Committed / Memory Compression / WS）在两臂间波动明显，**不作归因依据**。
