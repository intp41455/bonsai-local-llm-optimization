## 三、实测差异（逐项）

### 3.1 顶层结构

发出体 / A 转发 / B 转发的顶层键**完全一致**（8 个）：`chat_template_kwargs`、`max_tokens`、`messages`、
`model`、`stream`、`temperature`、`tool_choice`、`tools`。除 `messages` 外，逐字段 `A_eq_B` **全为 true**。

| 字段 | A_eq_B | A_eq_sent | 说明 |
|---|---|---|---|
| `model` / `max_tokens` / `stream` / `temperature` / `tool_choice` | true | true | 两臂原样转发 |
| `tools` | **true** | **true** | **两臂与发出体全等** → `tools.schema_hardening` 对本套 tools **未命中**（无改写） |
| `chat_template_kwargs` | true | **false** | **两臂都新增了该键且取值相同** `{"reasoning_effort":"medium"}` → 由 `--effort medium` 注入，**非两臂差异** |
| `messages` | **false** | false | 唯一实质差异，见 3.2 |

### 3.2 唯一实质差异：`messages[0]`（system）差 584 字符

`messages` 长度两臂同为 2（`system` + `user`），role 序列一致；`messages[1]`（user，59 字）**两臂相等**。

| 项 | A（v2） | B（v3） |
|---|---:|---:|
| `messages[0].content` 字符数 | **628** | **1212** |
| `sys_delta_chars` | — | **+584** |
| `B_sys_starts_with_A_sys` | — | **true** |
| 追加文本是否**逐字符等于** v3 的 `TOOL_POLICY_BLOCK` | — | **true**（`v3_TOOL_POLICY_BLOCK_chars=584`） |

B 相对 A 在 system **尾部**追加的 584 字符，即 `proxy\bonsai_proxy.py`（v3）的 `TOOL_POLICY_BLOCK`：

```
[tool-error recovery policy -- local runtime]
1) If the same tool returns the SAME error twice, never resend the identical call: ...
2) Never blindly repeat an action with side effects ...
3) Tool arguments must match the declared schema exactly ...
```

## 四、机制确认（由推断升为实测）

G6 §5.3 只证明「两臂请求不同」，本批**确认差异的唯一来源**：

1. 两臂**唯一的实质内容差异**是 `messages[0].content` 尾部追加的 **584 字符 = v3 的 `TOOL_POLICY_BLOCK`**；
2. 该块由 v3 的 `tools.error_policy=true` 触发（`apply_tool_error_policy()`：请求带非空 `tools`、
   首条为 `role=="system"` 且 `content` 为 str 时，把 `TOOL_POLICY_BLOCK` 追加到该 content 尾部）；
3. 其余所有候选改写**均已排除**：`tools` 两臂全等（`schema_hardening` 未命中）、
   `slimming.locations` 在 harness 自造 tools 描述里无 `(location: …)` 可命中、
   `chat_template_kwargs` 两臂相同（`--effort` 注入，非差异）。

→ **G6 中「B 比 A 多 119 token」的来源，实测等于该 584 字符策略块**（119 token ≈ 584 字符 / 4.9 字符每 token，
与 `budget.gate.chars_per_token_floor=3.0` 的保守口径方向一致）。即 v3 通过**改写 system 前缀**，
在 `temperature=0` 的确定性解码下改变了模型输出（G6 任务 8：A 合法 / B 非法）。

## 五、口径与局限（必须遵守）

1. **本批不产生模型输出**：桩立即返回最小 SSE，全程约 2 秒、无推理。本批只证明**转发内容差在哪**，
   **不构成任何能力或好坏判定**；G6 的「A 合法 / B 非法」仍是单任务 3 次样本。
2. **不得据此宣称「策略块有害」**：`TOOL_POLICY_BLOCK` 是为「工具错误连续重试」准备的常驻策略，
   其**收益场景本批未测**；本批只确认它**改变了输入**，未测其对通用任务的影响方向。
3. **B 臂用的是生产配置的副本**：仅改 4 个输出路径字段 + `prewarm.enabled=false`，行为段逐字段一致
   （驱动脚本打印 `behavior 段一致=True`）。B 臂脚本 sha256 `6ACFB9C5…` 与生产 `proxy\bonsai_proxy.py` 一致。
4. **A 臂（v2）的 CAP 硬编码副作用**：v2 无 `--config`，`CAP=r"D:\Bonsai-demo\capture"` 硬编码，
   故 A 臂桩测试在**生产抓包目录**留下 **1 个** `small_001_041931.json`（1917 B，即发出体）。
   该副作用**仅新增 1 个小请求抓包**，`capture\timings.jsonl` 行数 **905→905 未变**（未被写）。
5. **单请求**：本批每个代理只抓 **1 次** 转发体（确定性改写，同一输入结果恒定）；**未做多次重复**。

## 六、结论

1. **机制实测确认（非推断）**：A→B 转发内容的**唯一实质差异**是 v3 的 `tools.error_policy` 在首条
   system 文本尾部追加的 **584 字符常驻策略块**；`chat_template_kwargs`、`tools`、其余顶层字段两臂全等。
2. **对账闭合**：B−A = 590 字节 = 584 字符 + 6 个换行的 JSON 转义；A−发出体 = 56 字节 = `chat_template_kwargs`。
3. **不改动结论边界**：本批**不改变 G5/G6 主结论**，也**不支持「v3 更差」**；它只是把 G6 遗留的
   「机制待确认」**关闭**——两臂输出不同的原因，是 v3 改写输入（system 前缀）而非其它改写项。
4. **后续待办**：① 若关心策略块对通用任务的影响方向，需专门设计「带/不带策略块」的对照（同一 v3 代码，
   开关 `tools.error_policy`），本批不回答该问题；② 任务 10（压缩边界五轮）仍待补驱动。
