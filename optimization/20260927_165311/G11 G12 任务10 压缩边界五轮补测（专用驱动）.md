# G11 / G12 / G12b 任务10「压缩边界五轮」补测（专用驱动）

生成时间：2026-09-28 09:00　执行方：TRAE Agent

运行窗口：G11 07:22→07:30　G12 07:43→07:48　G12b（初版·偏差）08:29→08:33　G12b（隔离重跑）08:48→08:52

## 一、为什么做这一批

方案 §14.2 第 10 项要求「同一日志的固定切片，**同时做普通五轮和压缩边界五轮**……边界版用确定次数重复构造，
让实际模板 token 跨压缩阈值、但不超过后端硬上限」。
但 `changes.md §10.3` 长期记为「**未实现**（受 harness 能力限制）」：标准 harness（`bench_harness.py`）
的 12 项任务表里**没有任务 10 的定义**，其 `main()` 明确要求任务 10/11 走专用驱动。
本地也没有会做历史压缩的客户端（WorkBuddy / Pi），故「压缩」这一环只能由**驱动侧自建**。

本批补上这一项，并把「压缩边界」拆成两个可测、互不冒充的问题：

- **Q1 边界穿越·不压缩**：五轮累加固定切片，第 5 轮输入落入边界带 —— 闸门是否在生成前发现？后端是否仍在硬上限内？最初五条约束是否仍能列全？
- **Q2 边界 + 自建压缩器**：同一素材，驱动侧按 §E2 规则在越界前压缩已完成轮次 —— 削减是否**显式**（无静默裁剪）？压缩后五条约束是否仍能列全？工具配对是否完整？

## 五、G11 暴露的三个问题（本批不藏）

- **P1（驱动缺陷）C 档未压缩**：触发条件取自代理每轮返回的 `budget_check.input_tokens`，而本素材使闸门走便宜路径 → 该字段恒为 `null`（后端 `usage` 也未返回）→ 投影恒为 0 → **永不压缩**，C 档实际等同于 N 档。G12 改用自测精确投影修正。
- **P2（驱动缺陷）日志读取竞态**：响应返回后立即读转发日志，偶发读不到本请求记录（G11 C 轮 1 `record_seen=false`）。G12 改为 `find_rec_retry()`（12 次 × 0.5 s）修正。
- **F1（代理缺陷候选）便宜路径在边界上未告警**：见 §八。**非本轮驱动缺陷**，是生产代理的既有行为。

## 八、缺陷候选 F1：便宜路径的「保守上界」在 token 密集素材上失效

**现象**：`P-dense` 实际输入 **62,831 token > 阈值 56,320**，闸门仍报「在预算内(便宜路径)」
（`est_upper=42,399`），**未告警**。

**根因**：便宜路径以 `tokens ≤ body_bytes / 3.0` 为上界，其成立前提是素材 **≥ 3 字节/token**。
而日志切片类素材实测约 **1.87 字节/token**（1.85 字符/token），前提不成立，故 `bytes/3.0` 反而**低估**。

**判据（可计算，代入实测密度）**：便宜路径被采用 ⇔ `body_bytes ≤ 168,960`；设素材密度 `d`（字节/token），则

> 存在假阴性 ⟺ `56,320 · d < 168,960` ⟺ **`d < 3.0` 字节/token**

即：**密度低于所设 floor(3.0) 的素材，都存在一段「已超预算却仍被判在预算内」的输入区间**。

- `d = 1.87` → 假阴性区间为 token ∈ (56,320, **90,353**]；由于 90,353 > 硬上限 65,536，
  **该类素材即使输入超过后端硬上限，闸门也永远不会在生成前发现**。
- `d = 5.86`（sparse）→ `56,320 × 5.86 = 330,035 > 168,960` → 区间为空 → 必然进入精确计数并被正确判为超预算（与实测一致）。

**影响**：

1. 方案 §E 验收「超预算能在生成前被发现」**仅对 `d ≥ 3.0` 字节/token 的素材成立**；
   对本项目主力场景之一的「长日志 / 密集符号文本」不成立。
2. 极端情形下存在把超硬上限的输入直接送入后端的风险（当前 `mode=warn` 不阻断，实际风险取决于是否切 `reject`）。
3. 代价侧：精确计数实测耗时 **125 ms/次**（生产 sparse 记录 `elapsed_ms=125.0`），「总是精确计数」成本可接受。

**建议（本轮不改生产，待决策）**：把 `budget.gate.chars_per_token_floor` 从 3.0 下调到**真实下界**（如 1.5），
使便宜路径仅在「按最坏密度也不超预算」时才跳过精确计数；或对必须保证的路径强制精确计数。

## 十、诚实标注与口径边界

1. **专用驱动**：任务文本 / 夹具 / 编排与标准 harness 不同，本批**不能**与 G5/G9 的成功率相加。
2. **「压缩」是驱动侧自建**的规则化压缩器（按 §E2 的替换原则实现），**不是** WorkBuddy / Pi 的实测行为；
   §14.3 的 A/B/C 客户端口径**未**被本批覆盖。
3. 每档每探针 **n=1**（G12b 因偏差重跑，探针结论为 n=2 且完全一致）；n=1 只证明「本次可行/不可行」，不作复现性结论。
4. G11 的 `silent_trim_detected` 判据因 `usage`/`input_tokens` 均缺而**未实际生效**；G12 已改用自测精确投影补齐。
5. 压缩后仍列全五条约束，**部分**依赖 §E2「保留最初约束消息」的设计；未测「连最初约束也压缩」的极端情形。
