## 一、为什么做这一批

## 五、关键证据

### 5.1 G5 的截断假设被证实：轮 1 `finish` 由 `length` 变为 `tool_calls`

| 臂 | G5（max_tokens=4096）轮1 | G6（max_tokens=8192）轮1 |

| B | `length`（s1/s3） | `tool_calls`、工具调用 **1（write_file）** |

**两臂的轮 1 都不再被截断**，且都成功发起了 `write_file`。→ G5 §5.2 的「任务 8 在 4096 下不构成有效对照样本」
判断成立，放开预算后两臂均能产出 `results/pelican.svg`（G5 中 A 臂三样本连文件都没写出来）。

### 5.2 A 臂 3/3 通过；B 臂 3/3 失败，且失败点是**写出的 XML 非法**

B 三次失败项**完全相同**：`任务8 XML 合法 <- ParseError('duplicate attribute: line 7, column 36')`。
逐字节查看 `B-s8-*/results/pelican.svg` 第 7 行：

```
    <line x1="155" y2="95" x2="235" y2="95"/>
```

该行 **`y2` 出现两次、`y1` 缺失**（正确写法应为 `y1="95"`）。即 B 臂产出的是
**含重复属性的非法 XML**，`check_tasks.py` 因此判 FAIL；其余 5 项验收（存在 / ≤120 行 /
animate≥2 / 无外部资源 / 人工项）均通过。

A 臂 `A-s8-*/results/pelican.svg` 为 58 行、含 4 个动画元素、`ET.fromstring` 通过。

### 5.3 两臂送给后端的**首请求不同**（轮 1 直接可比）

轮 1 是两臂**完全相同的初始消息**（同一 system prompt + 同一任务原文），故可直接比对请求规模：

| 项 | A（v2 / :8082） | B（v3 / :8080） |
|---|---:|---:|
| 轮1 新评测 token（A: `prompt_n` / B: `prompt_evaluated_tokens`） | 522 | **641** |
| 轮1 复用 token（`cache_n` / `cache_reused_tokens`） | 109 | 109 |
| 轮1 请求总长（新+复用） | **631** | **750** |

**B 的首请求比 A 长 119 token**，且三次采样均一致。这说明两臂虽由同一 harness 发出**同一份输入**，
**代理层实际转发的请求内容不同**（B 侧更长）。这与 v3 配置中登记的确定性改写相符
（`config\bonsai-agent.json` 的 `tools.error_policy=true`「在第一条 system 文本尾部并入常驻策略块」；
`slimming.locations` / `tools.schema_hardening` 对 harness 这套自造 prompt/tools 无对应可命中项）。

**但本批未做请求体逐字节 diff，机制尚未确认**——只能确认「两臂请求不同」这一事实，
不能断言差异全部来自 `error_policy`。确认方法见第七节第 3 条。

### 5.4 两臂的收尾行为不同（如实记录，不作优劣推断）

- **A 臂：拿到有效交付物但从未自行终止。** 三次均跑满 `--max-rounds 16`（`stop=max_rounds`），
  轮 1 后连续 13 次 `write_file`/`run_python` 交替，`tool_retries=0`。
  验收只看产物，故 6/6 通过；但「不自行收敛」这一行为本身值得留痕。
- **B 臂：自行终止但交付物错误。** 11 轮 `model_finished`（末轮 `finish=stop`、`content=890` 字，即模型自述完成），

  最终把含重复属性的非法 SVG 当作完成品交付。
- A 臂另写了一个 `results/clean5.py`（55 B，内容是 `os.remove('results/clean4.py')`），
  `check_tasks.py` 任务 8 不校验多余文件，不影响判定。

## 六、口径与局限（必须遵守）

1. **与 G5 不可直接横比**：本批唯一改动是 `max_tokens` 4096 → 8192。G5 的任何数字（成功率、墙钟）
   都不能与本批放在同一张表里比较。本批唯一有效的比较是**批内 A vs B**（同 `max_tokens`）。
2. **样本极小 + 单任务**：每臂仅 3 次、仅任务 8 一项。**不能**由此推出「v3 整体更差」；
   G5 的主结论（无稳定提速、成功率经扣除后两臂相同）**不因本批改变**。
3. **墙钟不可当性能结论**：A 走满 16 轮、B 走 11 轮，且 A 轮 1 的思考量约为 B 的 2.4 倍
   （轮1 `reasoning` 字符数 A 12,986 / B 5,359），耗时差异主要来自轮次与思考量，**不构成代理性能对比**。
4. **失败已计入、缺失记 null**：6 次全部有记录，无缺失；A 臂 `config_hash` 为 null
   （修复前 v2 代理**不写** `logs\requests.jsonl`，该字段本就取不到，属设计如此，非采集失败），
   token 字段改按 `capture\timings.jsonl` **增量**取（16 条 = 16 轮，无一例降级）。
5. **不把推断写成确认**：§5.3 的「代理层改写」是**候选机制**，已标注未确认。

## 七、结论

1. **任务 8 不是 A 臂的能力缺口**：放开截断后 **A 3/3 通过**（`pelican.svg` 合法、含 4 个动画）。
   结合 5.1，可确认 G5 中任务 8 的 A 臂失败**纯由 `max_tokens=4096` 截断造成**。
2. **B 臂在任务 8 上稳定失败，且不是截断**：3/3 失败、输出逐字节相同，失败点是
   写出的 SVG **含重复属性**（第 7 行 `y2` 两次、缺 `y1`），属模型产出的**合法性问题**，
   与 `max_tokens` 无关（同一 8192 预算下 A 通过）。
3. **这是一个「与代理版本相关」的可复现差异**（不同于任务 7 的目录污染）：两臂同后端、
   同温度、同输入，但首请求规模差 119 token、输出确定性不同。**机制待确认**，建议下一步：
   用同一份请求体分别打到 :8082 与 :8080，dump 出代理实际转发的 JSON 逐字节 diff，
   定位是 v3 的哪一项确定性改写（首选 `tools.error_policy` 的常驻策略块）改变了模型输出。
4. **不要据此宣称 v3 更差**：单任务 3 次样本，且 A 臂自身表现异常（§5.4，跑满 16 轮不自终止）。
   本批的价值在于**把任务 8 从「截断失效」重新定性为「A 可做、B 稳定做错」**，
   并暴露了两个新问题：① 两臂请求内容并不相同；② B 的自检脚本为 0 字节、自检空转。
